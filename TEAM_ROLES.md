## Загальний огляд архітектури та зон відповідальності

Хоча концептуально система складається з **3 головних підсистем** (Агент журналу, Планувальник реплікації, Відновлювач), за алгоритмічними блоками курсу (п. 2 і п. 7 умови) вона розкладається рівно на **5 незалежних інженерних ролей**.

Такий розподіл дозволяє:
1. Кожному учаснику мати власну алгоритмічну зону для індивідуального оцінювання **D1** (базовий / просунутий / експертний рівень) на **Зрізі 0**.
2. Працювати паралельно без взаємних блокувань завдяки чітким інтерфейсам між модулями.
3. Повністю покрити всі **12 обов'язкових приймальних кейсів C1** та всі **6 обов'язкових експериментальних таблиць** для звіту.

  * Протокол навчання: запуск щонайменше з 3 різних ініціалізацій, вибір найкращої моделі за `macro-F1` на `valid.csv`.

* **Контракт модуля (API для команди):**

### Роль 3. Планувальник реплікації: ДП та жадібний розподіл (Підсистема 2: Планувальник)
**Відповідальний(а):** `olegstepanow12`  
**Обраний рівень D1 на Зріз 0:** `[ ] Базовий  [ ] Просунутий`

* **Основні задачі:**
  * Обчислення вартості $cost_i(r) = r \cdot w_i$ та корисності $u_i(r)$ події для кількості копій $r \in \{0, 1, 2, 3\}$ на основі класу (від Ролі 1), прапорця `critical` та коефіцієнтів надійності з `team_config.json`.
  * Реалізація **динамічного програмування (багатоваріантний рюкзак)** зі складністю $O(n \cdot W \cdot R_{\max})$ та **жадібного baseline** (додавання копії з максимальним $\Delta u / \Delta cost$) для вибору кількості копій у бюджеті вікна $W$.
  * Реалізація **жадібного алгоритму порядку реплікації та батчінгу**: розподіл копій на **різні** вузли (`A`, `B`, `C`), не більше одного batch на вузол за вікно, розмір $\le \text{max\_batch\_bytes}$, з урахуванням `reliability_weight` та залишкової місткості вузла.
  * Таблиці для звіту: «ДП проти жадібного» та «Вплив кількості копій (1/2/3) на $S, R, Q$».
* **Приймальні кейси C1:**
  * Кейс №6: ДП дає корисність не меншу за жадібний baseline на всіх виданих наборах.
  * Кейс №7: У штатному сценарії відновлено всі критичні події.
  * Кейс №8: У деградованому сценарії частка невідновлених критичних подій не перевищує поріг.
* **Варіанти рівня D1:**
  * *Базовий:* Багатоваріантний рюкзак (ДП + жадібний baseline) + евристика батчінгу по вузлах.
  * *Просунутий:* Задача Б — оптимальні контрольні точки журналу (snapshots) через ДП: $F[j] = \min_{i < j} (F[i] + \text{Snapshot}(i, j) + \text{RecoveryCost}(i, j))$, де результат не гірший за фіксований крок.
* **Контракт модуля (API для команди):**
  * `select_copies_dp(events, weights, utilities, budget_W) -> list[int]`
  * `schedule_batches(events, copies, node_configs, max_batch_bytes) -> dict[str, list[Record]]`

### Роль 4. Криптографічний захист, ГА та Модуль атаки (Підсистема 2/3: Безпека + Оптимізація)
**Відповідальний(а):** `roma245456i4j3frinin`  
**Обраний рівень D1 на Зріз 0:** `[ ] Базовий  [ ] Просунутий  [ ] Експертний`

* **Основні задачі:**
  * **Криптографія за стандартом Encrypt-then-MAC** (`FORMAT_SPEC_P3.md`):
    * Деривація ключа: `PBKDF2-HMAC-SHA256` (100 000 ітерацій, 16-байтова сіль, `dkLen=64` $\to K_{\text{enc}} = \text{master}[0:32], K_{\text{mac}} = \text{master}[32:64]$).
    * Шифрування: `AES-256-CTR`, лічильник `nonce(12) || uint32_BE(i)`, $i$ починається з `1`.
    * Автентифікація: `HMAC-SHA256` над відкритим заголовком і шифротекстом.
  * **Генетичний алгоритм (ГА):** налаштування параметрів системи (розмір вікна, поріг `NO_COMPRESSION`, коефіцієнт другої копії тощо) з турнірною селекцією, кросовером, мутацією та елітизмом. Порівняння з Random Search при однаковій кількості обчислень фітнесу.
  * **Модуль атаки:** ГА для відновлення ключа слабкого навчального шифру + тести модифікації байтів репліки для перевірки відхилення за HMAC.
* **Приймальні кейси C1:**
  * Кейс №10: Змінений шифротекст або HMAC гарантовано відхиляється.
* **Варіанти рівня D1:**
  * *Базовий:* Базовий криптомодуль (`AES-256-CTR` + `HMAC-SHA256`), ГА з хромосомою з 3 параметрів + елітизм + атака на слабкий шифр.
  * *Просунутий:* Розширена хромосома ГА (архітектура перцептрона, ваги планувальника, макс. копій), адаптивна мутація та локальний пошук.
  * *Експертний:* Багатокритеріальна оптимізація (фронт Парето за $S, R, T$) або DH / RSA-OAEP для сеансового ключа + вирівнювання метаданих реплік.
* **Контракт модуля (API для команди):**
  * `derive_keys(password: str, salt: bytes) -> tuple[bytes, bytes]`
  * `encrypt_and_mac(header: bytes, payload: bytes, password: str, salt: bytes, nonce: bytes) -> tuple[bytes, bytes]`
  * `verify_and_decrypt(header: bytes, ciphertext: bytes, mac: bytes, password: str, salt: bytes, nonce: bytes) -> bytes`
  * `run_genetic_optimizer(eval_fn, config) -> dict`

### Роль 5. Відновлювач, контейнер `LOG3` та Інтеграція (Підсистема 3: Відновлювач + Архитектор)
**Відповідальний(а):** `zxcboodya`  
**Обраний рівень D1 на Зріз 0:** `[ ] Базовий  [ ] Просунутий`

* **Основні задачі:**
  * Реалізація бінарного контейнера репліки `LOG3`: формування відкритого заголовка, збирання повного пакета (Заголовок + Стиснене й зашифроване навантаження + HMAC).
  * **Відновлювач (Recoverer):** читання вцілілих пакетів із `replication.py` (`surviving_blobs`), сувора перевірка полів заголовка (`magic == b"LOG3"`, `reserved`, розміри), перевірка HMAC і розшифрування, розпакування Гаффмана, **дедуплікація записів** з різних вузлів та відновлення впорядкованого журналу.
  * Захищена обробка пошкоджених пакетів (`reference/bad_*.bin`) без аварійного завершення та проходження всіх еталонних пакетів (`reference/ref_*.bin`).
  * Зведення наскрізного пайплайну з `replication.py`, обчислення метрик $S, R, T$ та єдиної оцінки $Q = \alpha S + \beta R + \gamma T$, автоматизація 12 тестів **C1** і таблиць впливу блоків для звіту.
* **Приймальні кейси C1:**
  * Кейс №11: Невірний пароль, обрізана репліка, поганий `magic` і `reserved` відхиляються без аварійного завершення (`expected_failures.json`).
  * Кейс №12: Усі еталонні пакети викладача (`reference/ref_*.bin`) читаються; повний прогін укладається в ліміт часу.
* **Варіанти рівня D1:**
  * *Базовий:* Контейнер `LOG3`, дедуплікація, всі еталонні та пошкоджені пакети, наскрізний оцінювач $Q$.
  * *Просунутий:* Крос-сумісність базового формату з іншою командою + інтеграція відновлення з просунутими розширеннями команди (snapshots / дельта-кодування).
* **Контракт модуля (API для команди):**
  * `pack_replica(records, password, compression_mode) -> bytes`
  * `unpack_replica(blob: bytes, password: str) -> list[Record]`
  * `recover_journal(surviving_blobs: list[bytes], password: str) -> list[Record]`
  * `evaluate_pipeline(session_data, scenario, seed, config) -> dict[str, float]` (повертає $S, R, T, Q$).
